# Camera Capture

Aparat: Canon EOS M50 Mark II przez USB — wyłącznie przez Canon EDSDK (Windows i macOS). Od 2.3 nie ma już gphoto2, wersji terminalowej (`main.py`/TUI) ani robota.

Pipeline:
1. **Capture** — Canon EDSDK, JPEG prosto do aplikacji (`SaveTo=Host`; format zdjęcia ustawiony w aparacie, L = Large Fine ~6000×4000).
2. **Clean BG** (zawsze ON, brak toggle w UI — celowo, bo i tak zostawiamy raw obok jako kopię) — wszystko liczone na pełnej rozdzielczości z aparatu, dopiero finalny kadr resize'owany do `OUTPUT_SIZE × OUTPUT_SIZE`:
   - rembg `u2netp` → maska → `_lift_internal_shadows` → auto-center: kwadratowy crop wokół bboxa produktu z `PRODUCT_MARGIN` → resize do canvas → `_build_shadow_layer` na canvas → kompozyt na białym tle.
3. **Overlay logo** w prawym dolnym rogu.
4. **Zapis** dwóch plików:
   - `photos/<nazwa>/photo_<timestamp>_raw.jpg` — kopia surowa z aparatu (przed obróbką).
   - `photos/<nazwa>/photo_<timestamp>.jpg` — końcowy 3000×3000.
5. **Upload do Automatu** (ON gdy `AUTOMAT_TOKEN` ustawiony; `--no-upload` wyłącza) — wysyłany jest **przetworzony** 3000×3000 JPEG (nie raw). Po `capture` od razu leci `announce_photo(filename)` (placeholder w UI Automatu, kafelek ze spinnerem), potem lokalny processing, potem `upload_processed(out, photo_id=announced_id)` PUT-uje plik do tego samego rekordu. W GUI upload to **osobny job `upload_photo` na końcu kolejki workera** (ten sam wątek, zero nowej współbieżności): przy strzelaniu seriami obróbka kolejnego zdjęcia nie czeka na sieć. Job niesie SWÓJ obiekt uploadera (zmiana sesji w międzyczasie nie przekieruje zdjęcia do cudzej sesji) i odpuszcza, gdy plik zniknął przed uploadem (BACKSPACE → kosz; PUT na martwy rekord kończyłby się retry POST-em wskrzeszającym zdjęcie po stronie Automatu). Wpis „Zapisano…" ma rozbicie czasów bez uploadu — upload loguje się osobno („↑ … w Automacie (N s)"). Raw nie idzie po sieci, tylko leży lokalnie.

Dlaczego ta kolejność: gdy crop 1:1 idzie pierwszy (centrowany na sensorze, bez znajomości pozycji produktu), produkt odsunięty od środka traci krawędź — auto-center umie tylko skalować w obrębie już-przyciętego kadru. Robiąc rembg + auto-center na full-res i dopiero wtedy 1:1 crop wokół bboxa, mamy dostęp do całego sensora i tylko jedno przeskalowanie.

Świadomie nie prostujemy zdjęcia: produktówki często strzelane są pod kątem 3/4 i auto-level by je rotował tak, żeby krawędź podstawy była pozioma — psując zamierzoną perspektywę. Z tego samego powodu nie honorujemy EXIF Orientation (`exif_transpose` nie jest wołany); jakby tag się pojawił — i tak go ignorujemy.

## Uruchomienie

```bash
source .venv/bin/activate
python3 gui.py              # okno aplikacji
python3 gui.py --browser    # to samo w przeglądarce
```

`activate` musi być **sourcowany** (`source` lub `.`) — `./venv/bin/activate` zwraca permission denied.

## Windows

Aplikacja okienkowa (`gui.py`) działa też na Windowsie — pełna instrukcja w `WINDOWS.md`. Aparatem steruje **wyłącznie Canon EDSDK** (`src/camera_edsdk.py`, przez `make_camera_session()` — po USB przez ctypes; **SDK żyje w osobnym procesie-dziecku** (`src/camera_proc.py`, `CAMERA_EDSDK_ISOLATION`, domyślnie ON), bo na niektórych maszynach wywołania EDSDK wisną NA ZAWSZE w DLL-u, a zawieszony proces — w odróżnieniu od wątku — zawsze da się zabić; wymaga `EDSDK.dll` + `EdsImage.dll` x64 z programu deweloperskiego Canona obok aplikacji — DLL-ek nie commitujemy, licencja; ich brak to czytelny błąd z `EdsdkSession.open()`). Backend digiCamControl (webserver HTTP pośrednika) został **USUNIĘTY w 1.1.0** — utrzymywanie dwóch ścieżek sterowania aparatem podwajało koszty debugowania, a EDSDK działa u operatorów; Instalacja: `pip install -r requirements-windows.txt`. Build `.exe`: `build_windows.bat` → PyInstaller z `CameraCapture.spec` (onedir, `dist\CameraCapture\Trixbrix - Camera Capture.exe`; ikona `assets/icons/trixbrix.ico`, metadane [autor: Michał Krzysteczko] generowane przez spec z `src/version.py` do `build/version_info.txt` — plik nie jest już trzymany w repo, żeby wersja miała jedno źródło prawdy; `.env` i `photos/` żyją obok `.exe`). CI: `.github/workflows/build-windows.yml` buduje artefakt `CameraCapture-windows` przy każdym pushu na main, a przy tagu `vX.Y.Z` dodatkowo publikuje GitHub Release z paczką `CameraCapture-windows-vX.Y.Z.zip` (patrz sekcja „Aktualizacje").

## Canon EDSDK także na macOS + ostrość w klikniętym punkcie

**macOS i Windows używają WYŁĄCZNIE Canon EDSDK** (od 2.3 gphoto2 jest usunięty z kodu; `CAMERA_BACKEND` w `.env` jest ignorowany). Na macOS SDK to `EDSDK.framework` w katalogu aplikacji (`find_edsdk_dll()` szuka binarki `EDSDK.framework/EDSDK`); bez niego aplikacja pokazuje kartę „Brak sterownika aparatu Canon" (`_edsdk_missing()` działa na obu systemach, tekst karty zależy od `state.platform`). Framework jest na licencji Canona i NIE jest w repo (`.gitignore`, jak `EDSDK.dll`); nagłówki do podglądu leżą w `.edsdk-headers/` (też poza repo). Różnice względem Windowsa w `camera_edsdk.py`: `ctypes.CDLL` zamiast `WinDLL`, callback `CFUNCTYPE` zamiast `WINFUNCTYPE`, bez COM, a pompa zdarzeń to `EdsGetEvent()` + jeden obrót `CFRunLoopRunInMode` (`_run_loop_once`). Framework pobrany przez Safari ma atrybut kwarantanny i dlopen go odrzuca („library load disallowed by system policy”) — `xattr -dr com.apple.quarantine EDSDK.framework` (podpis Canona zostaje ważny). Izolacja w procesie-dziecku (`camera_proc`) działa na obu systemach.

**Ostrość w punkcie** (`focus_at(fx, fy)`, ułamki klatki live view): współrzędne przeliczane na `Evf_CoordinateSystem`, ramka AF przez `EdsSetFramePoint` (SDK 13.18+; starsze — `Evf_ZoomPosition`), potem `DoEvfAf` ON, ~1,2 s pompowania zdarzeń, OFF. Front: klik w `#live` (kursor celownik, tylko gdy `state.focusSupported` = backend edsdk) → akcja `focus_at` → wątek camera; ramka `#af-box` pulsuje i robi się zielona/czerwona z `state.focus` (dopasowanie po `seq`). Działa tylko w trybie AF z wybieranym punktem; w twarz+śledzenie albo przy MF aparat ignoruje — błąd idzie do logu z podpowiedzią. Siatka kadrowania ma `pointer-events: none`, inaczej przechwytywała kliknięcia.

## Aplikacja okienkowa z live preview (`gui.py`, `src/webui.py`, `src/webui_static/`)

UI odwzorowane 1:1 z projektu Claude Design („Camera Capture.dc.html", projekt `a9cf1855-e687-4e6c-9b44-9d9066305f0a`). Natywne okno przez **pywebview** (WKWebView) z **systemowym paskiem tytułu** — prawdziwe traffic lights macOS (rysowane atrapy z mockupu wyleciały: nie działały w fullscreen). Start **zmaksymalizowany** (`maximized=True`, pywebview ≥5 — sztywne 1440×900 na małym laptopie wystawało poza ekran); `width/height` to rozmiar po odmaksymalizowaniu = ~85% ekranu z `webview.screens[0]` (fallback 1440×900, gdy enumeracja ekranów zawiedzie), min 1080×700, layout flexowy wypełnia okno przy każdym rozmiarze (bez skalowania transformem). W pasku zakładek siedzi TYLKO status połączenia „Aparat połączony · N fps" z ikoną SVG (`CAM_ICON`, kolor zielony/czerwony przez `currentColor`) — napisy `sesja:`/`zdjęć:` usunięte ŚWIADOMIE (nazwa sesji jest w sidebarze, liczbę zdjęć widać w filmstripie). Nazwa „Python" w menu bar zniknie dopiero po spakowaniu do .app (PyInstaller — niezrobione). Backend to lokalny serwer HTTP (stdlib, tylko 127.0.0.1, **losowy efemeryczny port + per-launch token** — request bez tokenu dostaje 403, więc UI nie jest osiągalne przeglądarką „z boku"; token idzie w URL przy pierwszym ładowaniu, potem HttpOnly cookie) serwujący `index.html` + statyki (`/static/style.css`, `/static/app.js` — whitelist rozszerzeń, bez podkatalogów), MJPEG stream live view (`/stream` — wysyłane są TYLKO nowe klatki: `WebUI.next_frame()` czeka na `Condition` z licznikiem klatek, zamiast pchać ostatnią klatkę w kółko w tempie `preview_fps`), `/api/state` (poll 500 ms; **log idzie przyrostowo** — front wysyła `?since=<seq>` i dostaje tylko ogon, pełną listę trzyma `logCache`/`mergeLog()` w `app.js`; wpis ma stałe `id` i rosnące `seq`, podbicie licznika ×N to nowy `seq` przy starym `id`; filmstrip w `state()` jest cache'owany po mtime katalogu sesji + `.review.json` i liczony POZA lockiem — wcześniej każdy poll globował katalog i parsował JSON pod globalnym RLockiem) i `/api/action` (dispatcher). `--browser` otwiera to samo w przeglądarce (fallback też gdy brak pywebview), `--port` przypina stały port.

```bash
python3 gui.py
python3 gui.py --name foo --no-upload --port 9000
```

**Ekran startowy**: dopóki sesja nie jest ustawiona, zakładka Sesja pokazuje listę sesji photo_studio z Automatu (`GET /api/photo_studio/sessions` → `[{id, name, product, created_at, photos_count}]`, `AutomatUploader.list_sessions()`) — **układ odwzorowuje Photo Studio w Automacie**: lewa oś dni (`dayRail()`, klik przewija do grupy) + kafelki z okładką pogrupowane nagłówkami dat (`groupByDay()`, polska odmiana przez `plForm/plSessions/plPhotos`). Na kafelku: okładka, nazwa, nazwa produktu albo „Sesja luźna", liczba zdjęć i godzina. Blok „Nowa sesja zdjęciowa" (duże pole + przycisk „Rozpocznij sesję") jest **wycentrowany**; pod nim po prawej mały input **filtra sesji** (`S.sessionFilter`, filtruje po nazwie sesji i produktu, obok „Odśwież listę"). Filtr od razu **zaznacza pierwszy wynik**: zaznaczenie kafelka (`S.pickIdx`/`S.pickList`, niebieska ramka) przesuwa się `↑`/`↓` z pola filtra (`←`/`→` zostają dla kursora), wszystkimi strzałkami poza polem, hover myszy też je przejmuje (hover i wybór klawiaturą to JEDEN stan — `paintPick()` tylko przemalowuje ramki, zero rebuildów), a **ENTER wchodzi w zaznaczoną sesję**. Filtr i zaznaczenie są zerowane przy wejściu i wyjściu z sesji. Stabilność layoutu: oba scrollowane kontenery mają `overflow-y: scroll` (znikający scrollbar przesuwał wszystko o 8 px przy krótkiej liście po filtrze), a odtwarzanie fokusa po rebuildzie idzie przez `focus({preventScroll: true})` — gołe `focus()` dowoziło input do widoku i resetowało przewinięcie listy przy każdej dolatującej okładce.

**Okładki sesji** (`_job_session_covers`, `photos/.covers/<id>.jpg`): lista z Automatu nie zawiera miniatur (`serialize_session` bez `with_photos` to same liczniki), więc robimy je u siebie z najnowszego zdjęcia sesji — **najpierw z lokalnego folderu** (`_local_cover_source()`, zero sieci; typowo tak powstaje większość), a dopiero dla sesji bez plików na dysku `GET /sessions/:id` + pobranie jednego zdjęcia (`download_photo(..., session_id=sid)` — uploader okładek nie ma otwartej sesji, więc id musi iść jawnie). Miniatura 420 px zostaje na stałe (~13 KB/sesja), więc kolejne wejścia nic nie ściągają. Job leci po `list_sessions` i **tylko przy zamkniętej sesji** — ekran startowy nie jest wtedy widoczny, a worker nie może opóźniać obróbki zdjęć. Błąd okładki nie przerywa listy, ale pierwszy jest logowany (cicha literówka w wywołaniu API zostawałaby w kodzie na zawsze). W UI kafelek bez okładki pokazuje skeleton i wypełnia się sam przy kolejnym poll-u; `#start-scroll` zachowuje pozycję przewijania między rebuildami, bo każda dolatująca okładka to rebuild ekranu. Klik w sesję = `set_session` z jej nazwą **i `session_id`** — klient podłącza się do istniejącej sesji Automatu po id (`AutomatUploader.attach_session()`, bez POST-a; Rails deduplikuje tylko per produkt+dzień, więc bez id klik w starą sesję zakładałby nową na dziś). Wpisanie w „Rozpocznij sesję" nazwy, która już istnieje na liście (case-insensitive, po sanityzacji), pokazuje dialog „Podłącz do istniejącej / Utwórz nową / Anuluj" (`S.pendingNew` w `app.js`; „Utwórz nową" = `set_session` bez id → POST, na inny dzień robi nową sesję, tego samego dnia Rails i tak zwróci istniejącą). `attach_to` w `WebUI` pamięta wybrane id — toggle uploadu OFF→ON re-attachuje zamiast otwierać nową; przy 404 (sesja zniknęła z Rails) `_reopen()` otwiera nową po nazwie jak dotąd. W sidebarze breadcrumb `Camera Capture / <nazwa sesji>`, pod nim nazwa sesji jako nagłówek i przycisk **Wróć** — jedno i drugie woła `leaveSession()` (`clear_session`, czyści też `attach_to`) i wraca do tego widoku. Pole do zmiany nazwy z przyciskiem „Ustaw" **usunięte** — nazwę wybiera się właśnie tu, na ekranie startowym (lista + „Rozpocznij sesję"), więc drugie wejście przez sidebar tylko dublowało tamtą ścieżkę, w dodatku bez dialogu „podłącz do istniejącej".

**Sync zdjęć z Automatem (dwustronny)**: po każdym udanym `open_session` zlecenie `(name, session_id)` idzie do **osobnego wątku sync** (`_sync_loop`/`_sync_session` w `webui.py`; kolejka `_sync_q`, zaległe zlecenia zwijane do ostatniego) — pobiera `GET /api/photo_studio/sessions/:id` i zrównuje filmstrip z sesją po drugiej stronie. Świadomie NIE job workera (był nim kiedyś): pobieranie kilkudziesięciu MB starej sesji wstrzymywałoby obróbkę zdjęć strzelonych zaraz po wejściu. Wątek ma **własny obiekt uploadera** (id sesji jawnie w wywołaniach — `requests.Session` nie jest bezpieczne dla dwóch wątków), przerywa pobieranie, gdy operator wyjdzie z sesji, a `.review.json` aktualizuje per plik pod `_review_lock` — recenzję piszą teraz dwa wątki (worker + sync), więc każdy cykl load→save w `webui.py` idzie pod tym zamkiem, a `save_review()` pisze przez tmp+rename (czytelnik w trakcie gołego zapisu dostawał ucięty JSON = pustą recenzję). **Automat jest źródłem prawdy**: czego nie ma lokalnie → ściągamy (`AutomatUploader.session_photos()` + `download_photo()` → `GET .../photos/:id/file`), czego nie ma już zdalnie → kasujemy lokalnie (`_prune_local()`).

Pobieranie: wejście w starą sesję na maszynie, która jej nie strzelała (inny komputer, wyczyszczone `photos/`), pokazuje jej zdjęcia w filmstripie zamiast pustki. Zapisywane są też `review["automat"]` (BACKSPACE kasuje wtedy zdjęcie i w Automacie) oraz `review["uploaded"]`. Raw nigdy nie szedł po sieci, więc wraca sam finalny JPEG — `raw/` nie jest odtwarzane. Nazwa pliku bierze się ze zdalnego `filename` (sam basename — zdalna nazwa nie może uciec z katalogu sesji, `_remote_filename()`), a przy jego braku z `photo_<id>.jpg`. Zdjęcia w statusie innym niż `processed` (placeholdery po announce) nie są pobierane.

Kasowanie (`_prune_local`) — operator odsiał zdjęcia w UI Automatu i filmstrip ma to odzwierciedlić. Pliki (finał + raw) idą do **kosza**, nie na śmietnik — patrz sekcja niżej. Dwa świadome zabezpieczenia, bo prune leci **automatycznie** przy wejściu w sesję:
- **Pusta lista zdalna = nie ruszamy nic.** Rails deduplikuje sesje per produkt + dzień, więc otwarcie wczorajszej sesji po samej nazwie zakłada nową, pustą — bez tego guardu prune wyczyściłby cały lokalny folder.
- Do prune liczą się **wszystkie statusy** zdjęć zdalnych (nie tylko `processed`) — placeholder po announce, w locie, też „istnieje" po drugiej stronie.

Gdy `GET /sessions/:id` zwróci **404** (całej sesji nie ma już w Automacie), `_sync_session` nie loguje błędu, tylko woła `_trash_session()`: lokalny folder ląduje w koszu, `name`/`attach_to` są czyszczone i UI wraca na ekran startowy — bez tego operator siedziałby w sesji, do której nic już nie doleci. 404 jest rozpoznawalny, bo `AutomatUploader._err()` rzuca dla niego `AutomatNotFound` (podklasa `RuntimeError`, więc stare `except Exception` łapią jak dotąd). **Nie** wnioskujemy o skasowanej sesji z listy `list_sessions()` — lista jest ograniczona (klient prosi o `?limit=1000`, sufit `INDEX_LIMIT_MAX` w trix-automat; bez parametru Rails oddaje 20, przez co starsze dni w ogóle nie docierały na ekran startowy), więc wszystko poza nią wyglądałoby na usunięte.

## Edycja logo na gotowym zdjęciu (podgląd → „Edytuj", klawisz E)

Panel z boku podglądu zdjęcia: bez logo / TRIXBRIX.eu / KIDS i róg kadru (`editPanelHtml()` w `app-session.js`). Zdjęcie obok to PRAWDZIWY wynik — `/edit_preview` renderuje go z wersji bez logo (zmniejszonej do 1400 px), nic nie zapisując. „Zapisz zdjęcie" = akcja `edit_save` → job `edit_logo`: wersja bez logo + `overlay_logo`, zapis atomowy w miejscu (nowe mtime = nowe `v` w adresie, miniatura odświeża się sama), meta w `.review.json` dostaje/traci „logo", a zdjęcie leci PUT-em do TEGO SAMEGO rekordu w Automacie (`review["automat"]`), nie jako nowe.

**Wersja bez logo** (`session_store.edit_base()`): `photos/<sesja>/.nologo/<plik>` — `process(..., base_out=...)` zapisuje ją przy każdej obróbce z logo. Zdjęcie zrobione bez logo (meta bez „logo") jest samo swoją bazą; przed nałożeniem logo kopiuje się do `.nologo/`, inaczej nie byłoby jak go zdjąć. Starsze zdjęcia: akcja `edit_prepare` → job `edit_base` robi bazę z oryginału z aparatu (`raw/`) z BIEŻĄCYMI ustawieniami obróbki (wynik może się minimalnie różnić od pierwotnego kadru). Bez `.nologo` i bez raw edycja jest niemożliwa i panel mówi to wprost. `shot_entries` niesie to jako `edit`: `ready` / `raw` / `""`. Kasowanie zdjęcia usuwa też jego `.nologo`.

## Rozgrzewka silnika czyszczenia tła — szacowany czas na danym komputerze

Każda udana rozgrzewka (`_job_warmup`) dopisuje swój czas do `.warmup.json` obok `.exe` (`WARMUP_FILE`, ostatnie `WARMUP_KEEP` = 10; obok `.env`, więc przeżywa aktualizacje). `_warmup_estimate()` = mediana ostatnich 5 (jedna anomalia — antywirus, pierwsza kompilacja po aktualizacji sterownika — nie psuje szacunku), liczona przy kolejkowaniu rozgrzewki i wysyłana jako `state.warmupEta`. Karta na podglądzie (`warmup-overlay`) pokazuje z niej „zwykle ok. X s na tym komputerze · zostało ok. Y s" i pasek postępu (zatrzymany na 95%, gdy trwa dłużej); bez historii zakłada 2 minuty (`WARMUP_DEFAULT_S` w `app-session.js`). Zapis atomowy, a katalog tylko do odczytu po prostu nie buduje historii.

## Kosz (`photos/.trash`, retencja `TRASH_RETENTION_DAYS`)

Nic, co aplikacja usuwa lokalnie, nie znika od razu — pliki lądują w `photos/.trash/<data>-<godzina>_<sesja>/` i dopiero `_job_purge_trash` (raz przy starcie, `purge_trash()` z `src/session_store.py`) kasuje wpisy starsze niż `TRASH_RETENTION_DAYS` (domyślnie 30). Odzyskanie = przeniesienie plików z powrotem do `photos/<sesja>/` (raw wraca obok finału, nie do `raw/` — kosz jest płaski).

Przez kosz idą obie ścieżki kasowania, wspólną metodą `_discard_files()`: **prune** przy synchronizacji i **świadome kasowanie** (BACKSPACE / „Odrzuć ostatnie" → `_job_delete`), a przez `_trash_session()` także cały folder sesji skasowanej w Automacie. Zabierany jest finalny JPEG **i jego raw**; miniatura z `.thumbs/` leci od razu na stałe (to cache, odtworzy się sama).

Data wieku wpisu siedzi w **nazwie** katalogu, nie w mtime — mtime zmienia się przy kopiowaniu/synchronizacji `photos/` i kosz czyściłby się losowo. `TRASH_RETENTION_DAYS=0` wyłącza kosz (kasowanie natychmiastowe, zachowanie sprzed tej zmiany).

Po stronie **Automatu kasowanie zostaje natychmiastowe** (`DELETE /photos/:photo_id` przy BACKSPACE) — soft delete rekordów to zmiana w trix-automat, świadomie nierobiona tutaj. Sync jest idempotentny — istniejące pliki nie są nadpisywane, więc kolejne otwarcia sesji nic nie ściągają. W UI pobieranie widać jako **kafelki-skeletony w filmstripie** (`WebUI.syncing` → `state["downloading"]` → klasa `.skeleton` w `style.css`, shimmer na tle i na pasku podpisu): tyle skeletonów, ile plików zostało do pobrania, każdy znika gdy jego plik wyląduje na dysku i zastąpi go prawdziwa miniatura. Skeleton znika też po **nieudanym** pobraniu (`finally`) — inaczej wisiałby do końca sesji. `st.downloading` jest w `sesjaKey`, czyli obsługiwane rebuildem jak `st.processing`, nie patchem w `updateVolatile()`.

**Żaden wątek nie może zginąć po cichu** (`_guarded()` w `webui.py`, opakowuje camera/worker/sync). Wątek, który wypada na nieobsłużonym wyjątku, nie zostawia w UI żadnego śladu: aplikacja działa dalej, tylko przestaje reagować. Przy aparacie objaw jest wręcz mylący — `connected` zostaje na `True`, MJPEG wisi na ostatniej odebranej klatce, a komendy piętrzą się w `_cam_q` (stąd wpis „aparat nie odebrał poprzedniej komendy (N w kolejce)"), więc wygląda to na zepsuty sprzęt, nie na błąd programu. Z tego samego powodu `_run_connected()` jest w `_camera_loop` owinięte w `except Exception`: wcześniej wychodził stamtąd każdy wyjątek spoza `CAMERA_ERRORS` (EDSDK przez ctypes potrafi rzucić `OSError`) i zabijał wątek zamiast wywołać reconnect. Po takiej wpadce `busy`/`capturing` są zerowane, bo obróbka mogła zostać przerwana w połowie i przycisk migawki zostałby na „Wyzwalam migawkę…" do końca sesji. Odmowy migawki (`_act_shoot`) też idą do logu i na przycisk — front tylko odpala animację i nie ogląda odpowiedzi, więc odrzucone ENTER wyglądało identycznie jak zdjęcie zrobione poprawnie. Gdy kolejka aparatu zalega, log dopisuje **fazę wątku** (`_cam_phase`: pobieranie klatki, robienie zdjęcia, odczyt kompensacji, łączenie) i jak długo w niej stoi. **Aparat wypadający z USB w trakcie zdjęcia** (druga obserwacja z tej samej maszyny): zdarzenia przestają przychodzić („Zdarzenia od aparatu: ŻADNYCH"), odczyty właściwości zwracają None (`SaveTo=None`), a uchwyt umiera na `0x0061 INVALID_HANDLE`. Dwie warstwy obrony: (1) pętla czekania na plik w `capture_to` NIE połyka już błędów EVF wskazujących na zerwane łącze (`_FATAL_LINK_CODES`: `0x61` + grupa `0xC0–0xC5`) — kończy czekanie po sekundach zamiast po 30+ s pełnego timeoutu z bezsensownym skanem karty na martwym uchwycie; (2) `_do_capture` w webui robi wtedy **jedną automatyczną ponowną próbę**: close → open (przy izolacji = świeży proces SDK) → strzał jeszcze raz — kadr się nie zmienił, produkt leży na stole, więc ujęcie nie ma prawa przepaść przez czkawkę USB. Watchdog ma przy tym próg **70 s dla fazy „robienie zdjęcia"** (strzał z awaryjnym pobraniem z karty legalnie trwa ~50 s — nie ma straszyć podczas normalnej powolnej operacji), a treść ostrzeżenia zależy od izolacji: z nią mówi o samoczynnym restarcie sterownika i wskazuje USB komputera, bez niej — każe wypiąć kabel.

Przy `CAMERA_EDSDK_ISOLATION` (default) zawieszki w DLL-u kończą się wcześniej i same — timeoutami RPC w `EdsdkProxy` (podgląd 12 s, strzał 90 s) i killem dziecka; watchdog niżej zostaje jako pas bezpieczeństwa i jedyna ochrona przy izolacji wyłączonej. Na tym siedzi **watchdog** (`_cam_watchdog`, wołany z każdego pollu `/api/state`): faza trzymana dłużej niż `_CAM_STUCK_S` (45 s — próg musi przeżyć strzał z awaryjnym pobraniem z karty) znaczy, że wątek wisi WEWNĄTRZ wywołania Canon SDK. Takiego wywołania nie da się przerwać z Pythona (ctypes w DLL-u), więc watchdog mówi operatorowi jedyną skuteczną rzecz: **odepnij i podepnij kabel USB aparatu** — zablokowana funkcja SDK wraca wtedy z błędem i pętla camera przechodzi w normalny reconnect. Jedno ostrzeżenie na epizod (klucz: znacznik czasu fazy), zaobserwowane w polu: **pierwsze** `EdsDownloadEvfImage` tuż po zdjęciu potrafi zawisnąć na dobre na niektórych maszynach (Ryzen 5800H + RTX 3080 — po każdym strzale; identyczny `.exe` na innym laptopie działa). Dlatego `capture_to()` w EDSDK kończy się `_settle_after_capture()`: ~0,6 s pompowania zdarzeń + ponowne ustawienie wyjścia EVF, czyli restart potoku podglądu tym samym zabiegiem, którym `_evf_paused` wskrzesza go po skanie karty. Poza tym `EdsDownloadEvfImage` (raz zbiegło się z ~107-sekundową kompilacją shaderów DirectML przy pierwszej rozgrzewce rembg), podczas gdy identyczny `.exe` na innym laptopie działa bez zarzutu.

Wątki (EDSDK wymaga wywołań z jednego wątku — aparat ma JEDNEGO właściciela):
- **camera** — sesja EDSDK (`make_camera_session()`) + pętla preview z throttlingiem do `preview_fps`; komendy przez `_cam_q` (shoot / set_camera); auto-reconnect co 5 s gdy init się nie uda lub podgląd padnie (np. inna aplikacja trzyma aparat). **Backoff przy „flapping"**: gdy połączenie pada szybciej niż `_HEALTHY_AFTER` (5 s) — typowo urządzenie PTP bez live view albo aparat w trybie odtwarzania — przerwa rośnie `RECONNECT_MIN`→`RECONNECT_MAX` (2 → 30 s), a cykl przechodzi w tryb cichy (`_run_connected(quiet=True)`): jedna linia ostrzeżenia zamiast pary „połączony"/„podgląd przerwany" co obrót. Wpis „Aparat połączony" wraca dopiero, gdy klatki polecą dłużej niż `_HEALTHY_AFTER`. `WebUI._log()` dodatkowo zwija powtórzony pod rząd wpis w licznik `n` (front dokleja „×N"), więc log w UI też nie puchnie.
- **worker** — `_jobs`: obróbka (announce → `process(out_name=...)` → przeniesienie raw do `raw/` → enqueue joba `upload_photo` — upload NIE blokuje obróbki następnego zdjęcia, patrz sekcja Pipeline pkt 5), batch, reprocess, delete, test. Strzały kolejkują się, preview nie zamiera. Na czas `process()` stdout jest przekierowany do logu UI (`_LogPipe` + `redirect_stdout`) — print()y z pipeline'u (pomiar czasu `clean_background`, ostrzeżenie o braku logo) w spakowanym `.exe` bez konsoli szły w nicość.
- **sync** — `_sync_q`: pobieranie zdjęć sesji z Automatu przy wejściu w sesję (patrz „Sync zdjęć z Automatem"). Osobny od workera, żeby sieć nie wstrzymywała obróbki; własny uploader, recenzja pod `_review_lock`.
- **HTTP** — ThreadingHTTPServer; stan pod RLock.

Zamykanie (`WebUI.stop()`, wołane po powrocie `webview.start()`): flaga stop → join wątku camera (timeout 4 s — wątek domyka sesję aparatu; porzucona otwarta sesja = BUSY przy następnym starcie) → join workera → shutdown serwera → `os._exit(0)` w `gui.py` (wiszące wątki C: EDSDK/onnxruntime/Cocoa potrafią zablokować normalną finalizację interpretera).

## Aktualizacje (GitHub Releases → samo-aktualizacja .exe)

Kanał wydań to **GitHub Releases** prywatnego repo `trixbrix/CameraCapture` (`GITHUB_REPO` w `src/version.py`). Artefakty CI się nie nadają — wymagają logowania i wygasają po 90 dniach.

**Token w `.exe`**: prywatne repo bez tokena odpowiada na `releases/latest` 404, a to updater czyta jako „brak nowszej wersji” — aktualizacje zniknęłyby po cichu. Dlatego workflow (krok „Embed update token”) wpisuje sekret repo `UPDATE_TOKEN` do `src/update_token.py` (w `.gitignore`) przed PyInstallerem i bez sekretu przerywa budowę. Token to fine-grained PAT z dostępem tylko do `trixbrix/CameraCapture`, uprawnienie Contents: read — każdy, kto ma `.exe`, może go wyciągnąć, więc nic więcej mu nie dawać. Ze źródeł token bierze się z `GITHUB_UPDATE_TOKEN` w `.env`. Paczkę pobieramy przez adres załącznika w API (`asset.url` + `Accept: application/octet-stream`), nie `browser_download_url`, który z prywatnego repo daje 404 nawet z tokenem.

**Wypuszczenie wersji jest automatyczne**: podbij `APP_VERSION` w `src/version.py` → commit → push na `main`. Workflow buduje `.exe` i w kroku „Publish release for APP_VERSION" sam zakłada `v<APP_VERSION>` (`gh release create --target <sha>`, tag powstaje przy okazji) z paczką `CameraCapture-windows-vX.Y.Z.zip`. Gdy release o tej wersji już istnieje, krok wypisuje komunikat i kończy się sukcesem — nic się nie nadpisuje, po prostu nie ma nowego wydania. Ręczne `git tag` nadal działa (trigger na `v*` + krok „Verify tag matches APP_VERSION" pilnuje, żeby ręczny tag zgadzał się ze stałą), ale nie jest do niczego potrzebne. Zip jest pakowany **z poziomu katalogu** `dist/CameraCapture` — na wierzchu leżą `.exe` i `_internal/`, bez katalogu-opakowania.

**Sprawdzanie** (`check_for_update()`): `GET /repos/<repo>/releases/latest`, porównanie `tag_name` z `APP_VERSION` przez `parse_version()`. Z tokenem (limit 5000 req/h) — w zupełności starcza — pytamy raz przy starcie (job `check_update` w kolejce workera) i na żądanie z Ustawień. Repo bez żadnego wydania zwraca 404 — traktowane jak „brak nowszej wersji", nie jak błąd.

**Karta Aktualizacji w Ustawieniach** pokazuje repozytorium (`GITHUB_REPO`, „prywatne", gdy w aplikacji jest token), zainstalowaną wersję, najnowsze wydanie z datą i czas ostatniego sprawdzenia. Dlatego `updater.latest_release()` zwraca najnowsze wydanie ZAWSZE, a „czy nowsze" rozstrzyga osobno `is_newer()`. WebUI trzyma je w `update_latest` / `update_checked`. „Wydanie na GitHubie" idzie akcją `open_url` do systemowej przeglądarki (pywebview otworzyłby stronę w oknie aplikacji); akcja przyjmuje tylko adresy `https://github.com/<GITHUB_REPO>…`.

**Instalacja** działa TYLKO dla spakowanego `.exe` na Windowsie (`can_self_update()` = `sys.frozen` + `win32`) — działającego procesu nie da się nadpisać, więc podmianę robi **`.exe` z pobranej paczki**, uruchomiony z flagą `--apply-update <katalog instalacji> <pid starej aplikacji>`:
1. `download_and_stage()` — zip do `PROJECT_DIR/.update/staging` (`_staging_root()`; `%TEMP%\cc_update` awaryjnie, gdy katalog aplikacji jest tylko do odczytu — wtedy błąd leci od razu do UI, zamiast wychodzić dopiero w aktualizatorze), rozpakowanie z odsianiem ścieżek uciekających poza katalog (zip-slip — paczka jest z sieci), progress w `state["update"]["progress"]`.
2. `_validate_staging()` — paczka MUSI mieć `.exe` i `_internal/`, inaczej stop. Bez tego aktualizator skopiowałby pustkę na działającą instalację i wyciął jej biblioteki przy sprzątaniu `_internal`.
3. `apply_update_and_restart()` — odpala `staging/<app>.exe --apply-update <PROJECT_DIR> <pid>` odłączonego (`DETACHED_PROCESS`), czeka 2 s i sprawdza `proc.poll()`: aktualizator ma teraz czekać na nas, więc jeżeli już nie żyje, to nowy `.exe` nie wstaje (brakująca biblioteka, blokada antywirusa) i **zostajemy w starej wersji** z błędem w logu. Dopiero **gdy to się uda** `WebUI._restart_into()` robi `stop()` (domknięcie sesji aparatu — porzucone PTP = BUSY po restarcie) i `os._exit(0)`.
4. `run_apply_update()` (w nowym procesie, `gui.py` łapie flagę PRZED resztą importów — aktualizator nie potrzebuje ani UI, ani aparatu): `_wait_for_old_app()` czeka uchwytem `OpenProcess`/`WaitForSingleObject` na zniknięcie starego pid-u, potem aż `.exe` da się otworzyć do zapisu → `_install()` kopiuje paczkę (`shutil`, retry na `PermissionError`) i `_prune_internal()` usuwa z `_internal` pliki, których nowa wersja już nie ma; reszta katalogu zostaje nietknięta (`.env`, `photos/`, ręcznie dołożony `EDSDK.dll` żyją obok `.exe`, patrz `PROJECT_DIR`) → start zainstalowanego `.exe`.
5. `cleanup_after_update()` — job `cleanup_update` przy starcie aplikacji kasuje `.update/` (i stare `%TEMP%\cc_update_*` po poprzednim mechanizmie) oraz czyta `update_error.txt`, jeśli poprzednia próba padła.

**Nie kasujemy katalogu, z którego coś jeszcze działa** (`_in_use()` — próba otwarcia `.exe` do zapisu; działający jest zablokowany). Aktualizator jest uruchomiony **właśnie ze staging**, a operator, któremu okno znika na kilka sekund, w tym czasie klika skrót i podnosi starą wersję — jej `cleanup_update` wyrywał wtedy aktualizatorowi biblioteki spod nóg i cała aktualizacja kończyła się `Failed to execute script 'pyiboot01_bootstrap' … No such file or directory: …\.update\staging\_internal\base_library.zip`. Ten sam guard stoi w `_staging_root()` (nowe pobranie nie czyści katalogu zajętego przez trwającą aktualizację, tylko schodzi na `%TEMP%`). Zaległości sprząta kolejny start. Do tego `apply_update_and_restart()` **ponawia uruchomienie aktualizatora raz**, jeśli ten padnie w ciągu 2 s — świeżo rozpakowany, niepodpisany plik potrafi polec na skanie antywirusa i wstać przy drugim podejściu.

Log siedzi **obok `.exe`** (`update.log`), pisze do niego i stara aplikacja, i aktualizator.

**Dlaczego nie `.bat` (poprzednia wersja, właśnie wyrzucona)**: skrypt cmd wymagał przepchania ścieżek przez kodowanie OEM i reguły cudzysłowów `cmd /c` — polskie znaki w profilu, spacja w `Trixbrix - Camera Capture.exe`, wolumen bez nazw 8.3 (`GetShortPathNameW` zwraca wtedy ścieżkę bez zmian) każde z osobna wystarczyły, żeby `robocopy` dostał zepsutą ścieżkę. A ponieważ proces szedł z `DETACHED_PROCESS`, cmd nie miał **żadnej konsoli**: `echo` leciał w próżnię, a gałąź `:failed` kończyła się `pause`, czyli niewidzialnym zawieszeniem. Objaw był zawsze ten sam i nie do zdiagnozowania: aplikacja znika, nic się nie dzieje, po ponownym uruchomieniu stara wersja. Aktualizator w Pythonie dostaje ścieżki jako listę `argv` (zero parsowania i kodowania), a przy wtopie pokazuje `MessageBoxW` z treścią błędu, zostawia `update_error.txt` i **podnosi z powrotem starą wersję** — operator nigdy nie zostaje z pustym pulpitem.

Czekanie na PID przez `tasklist` wyleciało wcześniej i nie wróciło: format wyjścia zależy od języka Windows. Uchwyt procesu takiej wady nie ma.

Uwaga przy testowaniu: aktualizację przeprowadza **stara** wersja, więc poprawka w `updater.py` działa dopiero na aktualizacjach *z* niej. Wersje ≤ 1.0.5 mają zepsuty mechanizm `.bat` i muszą raz zostać podmienione ręcznie (rozpakowanie zipa z Releases na katalog aplikacji).

**UI**: baner nad zakładkami (`updateBanner()` w `app.js`) — „Dostępna aktualizacja X.Y.Z" + „Zaktualizuj i uruchom ponownie" + „Później" (chowa do końca uruchomienia, per wersja). Aktualizacja jest odmawiana w trakcie zdjęcia/obróbki (`busy`/`processing`), a w drugą stronę — gdy `update_busy`, `_act_shoot` blokuje migawkę (zdjęcie zrobione tuż przed restartem zginęłoby razem z workerem, bo job nie doczekałby się obróbki). Progress pobierania jest ŚWIADOMIE poza kluczem shella (patchowany po `id` w `updateVolatile()`) — rebuild shella niszczy `<img>` streamu MJPEG, więc każdy procent oznaczałby miganie live view. Karta „Aktualizacje" w Ustawieniach ma wersję, „Sprawdź aktualizacje" i notatki z release'a. Sprawdzanie i pobieranie pokazują spinner (`.spinner` w `style.css`): `update.checking` jest ustawiane już w `_act_check_update` (jeszcze przed odpowiedzią na POST, więc łapie je pierwszy poll nawet gdy worker jest zajęty), a front trzyma go dodatkowo przez ~650 ms od kliknięcia (`S.checkStartedAt`) — odpowiedź z GitHuba potrafi wrócić w ~150 ms, czyli szybciej niż 500 ms poll, i spinner mignąłby bez śladu.

**Uruchomienie ze źródeł** (macOS/dev): `canApply=false` — UI tylko informuje, że jest nowszy tag i że aktualizuje się przez `git pull`.

Uwaga: `.exe` jest niepodpisany, więc SmartScreen może marudzić przy pierwszym uruchomieniu nowej wersji.

## Struktura

- `gui.py` — launcher aplikacji okienkowej (pywebview, natywny pasek tytułu; po zamknięciu okna `ui.stop()` + `os._exit(0)`; `--browser` = fallback w przeglądarce). Na samej górze pliku, PRZED importami `src/`, przechwycone `--apply-update` → `updater.run_apply_update()` (tryb aktualizatora, patrz sekcja „Aktualizacje").
- `src/cli.py` — `add_capture_args()`: flagi `gui.py` (name/logo/zoom/centrowanie/output-dir/upload); `--port`/`--browser` są w `gui.py`.
- `src/webui.py` — `WebUI`: backend aplikacji (wątki camera/worker, stan, joby) — patrz sekcja „Aplikacja okienkowa". Akcje z frontu i joby workera dispatchowane przez słowniki `_ACTIONS` / `_JOBS` (metody `_act_*` / `_job_*`). Warstwa HTTP i helpery plikowe wydzielone do dwóch modułów niżej.
- `src/webui_http.py` — klasa `Handler` (BaseHTTPRequestHandler): index.html + statyki (whitelist rozszerzeń, bez podkatalogów), MJPEG `/stream` (tylko nowe klatki przez `WebUI.next_frame()`), `/api/state` (z kursorem logu `?since=`), `/api/action`, `/img`. Sam transport — cała logika w `WebUI`; `ui` wstrzykiwane subklasą w `WebUI.start()`.
- `src/session_store.py` — czysta warstwa plikowa sesji (zero HTTP, zero stanu WebUI): review store (`.review.json`: `load_review`/`save_review`), `finals()`/`find_raw()`/`shot_entries()`, kosz (`trash_batch`/`move_into`/`purge_trash`), okładki (`cover_path`/`make_cover`), `remote_filename()`.
- `src/webui_static/` — frontend 1:1 z projektu Claude Design: `index.html` (szkielet strony), `style.css` (globalne style + `@font-face`; większość stylowania to inline style w template stringach JS — tak było w projekcie), logika JS podzielona na klasyczne skrypty ładowane kolejno (wspólny globalny scope, żadnych modułów ES — dawny pojedynczy `app.js`; gdy w tym dokumencie pada „app.js", chodzi o frontend jako całość): `app-core.js` (stan `S`, style, wspólne helpery: `evNumber`, odmiana PL, render logu), `app-start.js` (ekran startowy z listą sesji Automatu), `app-session.js` (zakładka Sesja: live view, filmstrip, overlay podglądu, EV), `app-settings.js` (zakładka Ustawienia + akcje aktualizacji), `app-main.js` (shell, render keyowany, klawiatura, pętla `/api/state` — MUSI być ładowany ostatni, bo odpala `tick()`), `plex-mono-*.woff2` (IBM Plex Mono 400/500, latin + latin-ext — font bundlowany lokalnie, UI działa offline; zero zewnętrznych zależności sieciowych).
- `src/naming.py` — `sanitize_name()`.
- `src/camera.py` — `make_camera_session()` (zawsze EDSDK: `EdsdkProxy` w procesie-dziecku albo `EdsdkSession` przy `CAMERA_EDSDK_ISOLATION=false`; zwracana sesja niesie `backend_info` — skąd wzięty SDK albo że go BRAK — logowany jako pierwszy wpis) i `CAMERA_ERRORS` (tupla błędów aparatu łapana przez webui).
- `src/camera_proc.py` — EDSDK w osobnym procesie: `run_edsdk_server()` (pętla RPC w dziecku — JSON po liniach na stdin/stdout, klatki podglądu w base64, hooki `on_log`/`on_status` jako ramki `event`; jednowątkowa i blokująca Z PREMEDYTACJĄ — gdy SDK zawiśnie, wisi całe dziecko, a rodzic je zabija) i `EdsdkProxy` (ten sam interfejs co `EdsdkSession`; **dwa limity na operację**: całkowity w `_TIMEOUTS` i limit CISZY w `_QUIET_LIMITS` — w trakcie strzału dziecko nadaje co sekundę status „Czekam na plik…", więc 15 s bez żadnej ramki znaczy zawieszkę w DLL-u i nie ma po co czekać do końca limitu całkowitego, np. gdy `EdsDownload` utknie przy pobieraniu pliku; po przekroczeniu kill dziecka + `CameraProcError` ⊂ RuntimeError ⊂ `CAMERA_ERRORS` → pętla camera robi zwykły reconnect). **Każde `open()` = nowe dziecko = świeży `EdsInitializeSDK`** — to rozwiązuje też zatrute SDK po ręcznym wypięciu kabla (błąd `0x0061 INVALID_HANDLE` przy każdej kolejnej próbie, bo Terminate→Initialize w jednym procesie kończy się access violation). Dziecko to ten sam program (`gui.py --edsdk-server` / `.exe --edsdk-server`, łapane przed ciężkimi importami jak `--apply-update`; w serwerze `sys.stdout` jest podmieniany na stderr PRZED importem camera_edsdk, bo stdout to kanał RPC). Zawieszka zmienia się z „aplikacja do restartu + kabel" w kilkunastosekundową czkawkę naprawiającą się samą, bez uprawnień administratora. Dziecko **nigdy nie pokazuje dialogu PyInstallera**: cała pętla jest opakowana w `except BaseException` (windowed build wyświetla MessageBox przy nieobsłużonym wyjątku — wyskakiwał operatorowi, gdy osierocone dziecko po minutach próbowało pisać w martwą rurę, `OSError 22`), a `send()` na martwej rurze kończy proces po cichu. Rodzic ubija dziecko także przy zamykaniu aplikacji (`EdsdkProxy.terminate()` wołane na początku `WebUI.stop()` — bezpieczne z innego wątku, bo to operacja na procesie; kończy też blokujące RPC w wątku camera, więc join przy stop() nie stoi pełnego timeoutu). Wyłącznik: `CAMERA_EDSDK_ISOLATION=false` = SDK w procesie aplikacji (stare zachowanie).
- `src/camera_edsdk.py` — `EdsdkSession`: backend aparatu dla Windows przez Canon EDSDK (ctypes, `EDSDK.dll` + `EdsImage.dll` x64 obok aplikacji lub `EDSDK_DLL` z .env; `find_edsdk_dll()` używane też przez fabrykę do auto-wyboru). **SDK ładowane i inicjalizowane RAZ NA PROCES** (`_SDK`/`_SDK_INITIALIZED` na module) — `close()` zamyka tylko sesję aparatu, ŚWIADOMIE bez `EdsTerminateSDK` i bez `CoUninitialize`: cykl Terminate→Initialize w tym samym procesie kończy się w EDSDK access violation przy drugim podejściu (zaobserwowane w polu: chwilowy błąd EVF ubijał sesję, a każda próba reconnectu co 5 s padała na „access violation reading 0x…50" aż do restartu aplikacji; OS sprząta przy wyjściu procesu, `gui.py` i tak kończy przez `os._exit`). Live view = EVF memory stream (`EdsDownloadEvfImage`; `preview_frame()` ponawia 2× W MIEJSCU chwilowe błędy `INTERNAL_ERROR` 0x0002 / `OBJECT_NOTREADY` / `DEVICE_BUSY` — webui na każdy wyjątek podglądu odpowiada pełnym close/open sesji, więc czkawka EVF przy zapisie/AF nie może być pretekstem do zrywania połączenia); wyjście EVF ustawiane na **TFT|PC (3)** — podgląd idzie na komputer i na ekran aparatu jednocześnie (wyjście to maska bitowa; wartość czytana z powrotem i przy odrzuceniu/przycięciu fallback na samo PC z wpisem w logu — ekran aparatu wtedy gaśnie, jak dawniej). Strzał = `PressShutterButton` + `SaveTo=Host` (plik leci do nas przez pamięć, nie na kartę SD; czekanie na zdarzenie z plikiem, pompowane `EdsGetEvent` — jak w konsolowym przykładzie Canona). Za uchwyt do pobrania robi **każde** zdarzenie niosące plik (`_OBJECT_EVENTS_WITH_ITEM`: `DirItemRequestTransfer` 0x208, `…DT` 0x209, `DirItemCreated` 0x204) — to ostatnie przychodzi, gdy zdjęcie mimo wszystko poszło na kartę, a ściągnąć da się je tak samo. Czekanie wyłącznie na 0x208 kończyło się zawieszeniem na „Wyzwalam migawkę…". Wszystkie wywołania z jednego wątku (camera w webui). **`CoInitializeEx` (STA) w tym samym wątku, przed `EdsInitializeSDK`** — na Windowsie EDSDK dostarcza zdarzenia aparatu kolejką komunikatów COM, którą zbiera `EdsGetEvent()`. Bez tego migawka strzela normalnie (to zwykła komenda po USB), ale `DirItemRequestTransfer` nigdy nie dolatuje i aplikacja stoi na „Wyzwalam migawkę…" aż do timeoutu — objaw myli, bo aparat słychać, więc wygląda na zawieszenie aplikacji. `EdsSetCapacity` jest odświeżane PRZED każdym strzałem: aparat odejmuje sobie zadeklarowane miejsce po każdym zdjęciu i po kilku ujęciach przestaje oddawać pliki, bez żadnego błędu. Kody wszystkich odebranych zdarzeń i odczytane z powrotem `SaveTo` lądują w komunikacie timeoutu — bez nich diagnoza sprowadzała się do zgadywania, czy aparat milczy, czy przysyła coś innego niż oczekujemy. W pętli czekania podgląd EVF jest **ciągnięty dalej** (klatki do kosza): w GUI Canona pętla EVF chodzi przez cały czas robienia zdjęcia, a bezlusterkowiec potrafi stanąć w połowie transakcji, gdy host przestaje odbierać EVF. **Kolejka komunikatów Windows jest pompowana razem z `EdsGetEvent()`** (`_pump()` → `PeekMessage`/`TranslateMessage`/`DispatchMessage`, max 32 komunikaty na obrót): STA dostarcza wywołania COM przez ukryte okno, a wątek camera własnej pętli komunikatów nie ma — samo `EdsGetEvent()` wystarcza w aplikacji konsolowej, która i tak w takiej pętli stoi. Bez pompy zdarzenie z plikiem nigdy nie dolatywało mimo poprawnego `CoInitializeEx`. **Wszystkie funkcje EDSDK mają komplet `argtypes`**: bez nich ctypes przepycha Pythonowego inta jako 32-bitowy `int`, a `EdsBaseRef` na x64 to wskaźnik powyżej 4 GB — uchwyt złapany w callbacku obiektowym docierał do `EdsGetDirectoryItemInfo`/`EdsDownload`/`EdsRelease` obcięty do połowy. **Awaryjne pobranie z karty** (`_download_newest_from_card`, po `_CARD_FALLBACK_S` = 8 s ciszy zamiast czekania do pełnego timeoutu): live view jest gaszony na czas skanowania (`_evf_paused` — aparat potrafi zignorować listowanie karty przy włączonym EVF), `_scan_children()` schodzi wolumen → DCIM → 100CANON → pliki i bierze najnowszy po `dateTime`, którego nie ma jeszcze w `self._downloaded`. Ten zbiór nazw jest anty-duplikatem: gdy zdjęcie w ogóle nie powstało, jedynym kandydatem jest poprzednie ujęcie, które już tam siedzi i zostaje odrzucone. ## Auto-center

Liczę bbox z maski binarnej, skaluję obraz tak żeby produkt mieścił się z `PRODUCT_MARGIN` z każdej strony, i przesuwam tak żeby środek bbox = środek kadru. Kompozytuję `image.paste(img, (paste_x, paste_y), mask=soft_mask)` — `soft_mask` to alpha z rembg z lekkim blurem (`CLEAN_BG_EDGE_BLUR=0.6`).

**Zoom i centrowanie to dwa niezależne toggle** (`auto_zoom` / `auto_center`, UI: `z` / `c`, CLI: `--no-auto-zoom` / `--no-auto-center`). Cztery kombinacje w `clean_background`:
- **zoom ON + center ON** — pełna maszyneria opisana niżej (bleed-fit, small_product itd.).
- **zoom ON + center OFF** — okno cropu zoomowane do bboxa (fit-both z `PRODUCT_MARGIN`), ale kotwiczone proporcjonalnie do pozycji produktu w source (produkt odsunięty od środka kadru zostaje odsunięty w canvy). Okno clampowane tak, żeby zawsze objęło cały bbox — produkt przy krawędzi kadru nie jest ucinany, ląduje przy krawędzi canvy.
- **zoom OFF + center ON** — naturalne okno (największy canvas-aspect prostokąt w source, jak small_product) wycentrowane na bboxie, clamp do granic source.
- **zoom OFF + center OFF** — centralny crop sensora bez patrzenia na produkt (produkt mocno poza środkiem może być ucięty krawędzią cropu — to świadome „nie ruszaj nic").

Bleed-fit i small_product działają tylko przy obu ON.

**Wyjątek — bleed off-frame**: `_image_bleed_edges()` zwraca dict `{left, right, top, bottom: bool}`. Pasek 0.5% szerokości od każdej krawędzi sprawdzany na surowym obrazie (nie na masce — u2netp @ 768 inference potrafi obciąć cienkie wystające fragmenty np. szynę sięgającą krawędzi, więc bbox by pudłował). Próg `bg_lum * 0.7` z `bg_mask` (alpha < 32) — fallback 95-percentyl jeśli tła za mało; min 50 ciemnych pikseli na pasek żeby uznać krawędź za bleedującą.

Auto-center wybiera ścieżkę po trzech sygnałach: **rozmiar produktu względem source** (`max(bw/src_w, bh/src_h)` < 0.30 = small product), **kształt bboxa względem canvy** (`bw/bh` vs `canvas_aspect`, ±5% tolerancji) oraz **bleed na choćby jednej krawędzi danej osi**:

- **any_x_bleed + any_y_bleed** (np. krzyżak torów ucięty przez wszystkie krawędzie source) — sprawdzany PRZED wide/tall. Żadnej osi nie da się „zfitować" bez pokazania amputowanej krawędzi cięcia pływającej w kadrze z białym marginesem. Crop = największe canvas-aspect okno mieszczące się W CAŁOŚCI w source (dla 1:1 z 3:2: `crop_h = src_h`, `crop_w = src_h`). Anchor per-oś: jedna strona bleeduje → bbox edge nie-bleedującej strony + `PRODUCT_MARGIN`; obie bleedują → środek bboxa. Na końcu clamp okna do granic source — biały padding po bleedującej stronie odsłoniłby cięcie. Efekt: każda ucięta krawędź ląduje na/za krawędzią canvy i produkt wizualnie kontynuuje off-frame na obu osiach.

- **small_product** (np. LEGO 2x2 w środku kadru — bbox ~600×600 z source 6000×4000 = fill_ratio 0.15) → preserve natural framing. Crop window = największy canvas-aspect prostokąt który mieści się w source (dla 1:1 canvy z 3:2 source: `crop_h = src_h, crop_w = src_h * canvas_aspect = src_h`). Scale = `canvas_h / src_h` = 0.375. Bbox w canvy zachowuje swoją source-frame proporcję — produkt nie jest agresywnie zoom'owany. Bleed-fit pomijany dla small_product, bo małe produkty nie bleedują.

- **wide_product + any_x_bleed** (bbox wyraźnie szerszy niż canvy spinanie X — np. szyna buforem wystaje poza lewą lub prawą lub obie) → fituj Y, X overflow off-canvas. `crop_h = bh / bleed_inner` (z `BLEED_FIT_MARGIN`), `crop_w = crop_h * canvas_aspect`. Po wyznaczeniu jest **clamp `crop_w ≤ bw`** żeby zbyt duży margin nie wepchnął bleedującej krawędzi bbox-a w canvy (i nie zabił bleed-effectu). Anchor:
  - **non-bleeding side X**: `bbox edge + PRODUCT_MARGIN`. Np. lewa bleed, prawa nie → `sr = bbox.r + crop_w*PRODUCT_MARGIN`, więc bbox.r jest 15% canvy od prawej krawędzi (przestrzeń pod logo). Lewa strona bbox-a wychodzi poza lewą canvy (bleed).
  - **non-bleeding side Y**: `bbox edge + PRODUCT_MARGIN`. Np. dół bleed, góra nie → `sb = bbox.b + crop_h*PRODUCT_MARGIN`, czyli bbox.b 15% nad canvas bottom. To zostawia czystą strefę dla logo (bottom-right), góra dostaje resztę crop window (zwykle białe niebo/ściana ze source nad bboxem ~30-40% canvy).
  - **bleeding side**: nie adjustowany — wynika z anchor non-bleeding (`sl = sr - crop_w` lub `st = sb - crop_h`). Bbox edge na bleedującej stronie ląduje poza canvy, produkt wizualnie kontynuuje off-frame.
  - obie strony X bleedują → cx = bbox center; analogicznie obie Y bleedują → cy = bbox center.
- **tall_product + any_y_bleed** → symetrycznie: fituj X, Y overflows.
- inne kombinacje (wąsko/wysoki produkt centrowany bez bleeda, single-edge bleed na osi prostopadłej do dominującego wymiaru itd.) → standardowy fit-both (`crop_w = bw/inner`, `crop_h = bh/inner`, większy wymiar dyktuje skalę → produkt centrowany z `PRODUCT_MARGIN` ze wszystkich stron) **z kotwiczeniem bleedu**: jeżeli któraś krawędź bleeduje (typowy przypadek: kwadratowy bbox ~1.0 wpadający w ±5% martwą strefę wide/tall + dolny bleed), okno cropu na tej osi nie jest centrowane, tylko kotwiczone do bleedującej krawędzi source (`st = src_h - crop_h` dla dolnego bleedu itd.) — cięcie z raw ląduje dokładnie na krawędzi canvy i produkt wizualnie kontynuuje off-frame, zamiast pływać nad białym marginesem. Obie krawędzie osi bleedują → crop capowany do rozmiaru source na tej osi i clamp do środka. Krawędzie bez bleedu → normalne centrowanie/margines.

Założenie: produkt szerszy niż canvy w 1:1 nie da się zmieścić w całości — fit-both go zmniejsza i zostawia pasy białego po bokach (na drugim outpucie #12). Y-fit z anchor-do-bbox-edge na nie-bleedującej stronie zachowuje skalę produktu i naturalną kompozycję źródła (np. niebo/ścianę nad produktem).

## Shadow handling

Dwie funkcje w `src/background.py`:

### `_build_shadow_layer()`
Warstwa cienia STRICTLY pod produktem (per-column bottom + horizontal bbox margin):
1. Dla każdej kolumny x liczy `ref_y[x]` = najniższy fg pixel w tej kolumnie (lub bbox bottom dla kolumn-przerw).
2. Cień rozciąga się tylko poniżej `ref_y[x]` (`dy = y - ref_y[x] >= 0`).
3. Falloff exponential: `proximity = exp(-3 * dy / shadow_radius_px)` — gładkie wygaszenie do zera, brak twardej krawędzi.
4. Gating horyzontalny: tylko kolumny w bbox produktu + 3% marginesu po bokach.
5. `darkness * SHADOW_STRENGTH * proximity` przyciemnia białe tło.

### `_lift_internal_shadows()`
Przy `SHADOW_STRENGTH=0` (default) **early-return bez liczenia czegokolwiek** — lift wychodzi wtedy matematycznie zerowy, a sama arytmetyka to kilka macierzy float32 na pełnych 24 MP (>1 GB szczytu pamięci); na maszynach z małym RAM-em wpychało to obróbkę w swap i „czyszczenie tła" potrafiło trwać wielokrotnie dłużej niż samo rembg.

Lifting cieni widocznych przez prześwity produktu (np. między elementami szyny):
1. Wykrywa piksele "jasne ale przyciemnione" (`lum/bg_lum` w przedziale `[0.55, 0.95]`) — to typowo cień na białym stole widoczny przez gap w produkcie.
2. Te piksele podciągane do bieli proporcjonalnie do darkness × strength.
3. Szare ciało produktu (`lum/bg_lum < 0.55`) NIE jest ruszane.

Aplikowane na obrazie ŹRÓDŁOWYM przed paste, dzięki czemu po `canvas.paste(img, mask=soft_mask)` prześwity wyglądają czysto.

## Pozycja logo

Domyślnie prawy dolny róg (`image_processing.py:overlay_logo`).
- `LOGO_ENABLED=True` — nakładanie logo w ogóle; CLI `--no-logo` wyłącza na czas uruchomienia.
- `LOGO_POSITION="bottom-right"` — róg logo (`bottom-right`/`bottom-left`/`top-right`/`top-left`, walidacja w `LOGO_POSITIONS`; nieznana wartość → fallback bottom-right z warningiem); CLI `--logo-position`.
- `LOGO_HEIGHT_RATIO=0.06` — wysokość logo / wysokość kadru dla pliku spoza `LOGOS` (tylko `--logo` w CLI; w GUI logo wybiera się z `LOGOS`).
- `LOGO_MARGIN_RATIO=0.04` — margines od krawędzi / szerokość kadru.
- `LOGO_OPACITY=0.5` — stałe krycie watermarku dla pliku spoza `LOGOS`. Suwak „Krycie" w GUI usunięty ŚWIADOMIE — wartość nie jest zmienialna z UI.

Uwaga: anchory bleed-fit w auto-center (sekcja wyżej) zakładają logo w prawym dolnym rogu — zostawiają czystą strefę bottom-right. Przy zmianie `LOGO_POSITION` na inny róg bleed-fit nadal chroni bottom-right, nie nowy róg (świadome uproszczenie; regularne fit-both ma margines ze wszystkich stron, więc tam bez różnicy).

## Upload do Automatu (Rails)

Endpointy:
- `POST /api/photo_studio/sessions` — body `product_name=<sanitized name>`. Rails szuka produktu (case-insensitive exact). Znalazł → bindowana sesja (idempotentne per dzień + produkt). Nie znalazł → sesja luźna z labelem = wpisana nazwa, **bez 404**. Response: `{id, name, product_id, product_found, reattached, photos_count}`.
- `POST /api/photo_studio/sessions/:id/photos` z `data={filename}` — `announce_photo`, tworzy placeholder; zwraca `{id}`.
- `PUT /api/photo_studio/sessions/:id/photos/:photo_id` z multipart `file=` — `upload_processed`, podpina przetworzony JPEG do placeholdera. Bez `photo_id` leci POST na ten sam URL bez `:photo_id`.
- `GET /api/photo_studio/sessions/:id` — sesja z listą zdjęć (`photos: [{id, status, filename, processed, raw_filename, error_message}]`), źródło prawdy dla `sync_session`.
- `GET /api/photo_studio/sessions/:id/photos/:photo_id/file` — przetworzony JPEG z powrotem (`send_data`, Bearer jak reszta API — bez publicznych URL-i Active Storage). Dodane w trix-automat razem z tą zmianą; **wymaga deployu Automatu**, bo bez tego endpointu klient dostaje 404 i nic nie pobierze.

Wszystko z nagłówkiem `Authorization: Bearer <AUTOMAT_TOKEN>`. Sesja otwiera się przy starcie, przy `n` (zmiana nazwy) i przy `u` ON. Flow strzału: `capture` → `announce_photo(...)` (UI Automatu od razu pokazuje kafelek ze spinnerem) → lokalny processing → `upload_processed(..., photo_id=announced)`.

**Auto-retry przy 404**: jeżeli sesja zniknęła po stronie Rails (restart bazy, czyszczenie), zarówno `announce_photo` jak i `upload_processed` raz odtwarzają sesję przez `_reopen()` i powtarzają operację. Przy upload retry leci jako POST bez `photo_id` (stary id z poprzedniej sesji jest martwy, robimy nowy rekord).

Błędy uploadu są logowane w logu UI — nie wywalają pętli.

`.env` (gitignored, patrz `.env.example`):
```
AUTOMAT_URL=http://localhost:3000
AUTOMAT_TOKEN=<hex>
AUTOMAT_UPLOAD_ENABLED=true
```

## Znane problemy z aparatem

- **Zwis na „Łączę z aparatem…"** — Photos.app / Image Capture / Canon EOS Utility przejmują urządzenie. Zamknij przed startem.
- **Zdjęcia „obrócone" o 90°** — pipeline NIE honoruje EXIF Orientation (świadomie — przy strzałach 3/4 nie chcemy, żeby zdjęcie się rotowało). Gdy aparat zapisuje orientację: Menu aparatu → Setup → Auto Rotate → Off.

## Konwencje

- **Każdy commit podbija wersję — bez wyjątków**: przed `git commit` podnieś `APP_VERSION` w `src/version.py` (patch przy poprawkach i drobiazgach, minor przy nowej funkcji) i włóż tę zmianę do TEGO SAMEGO commita. Dotyczy też commitów z samą dokumentacją — reguła ma być bezmyślna do stosowania, a nie do rozważania „czy ta zmiana trafia do `.exe`".
  - **Wydanie robi się samo**: push na `main` = build + `gh release create v<APP_VERSION>` (krok „Publish release for APP_VERSION"). Ręczne tagowanie nie jest potrzebne — tag zakłada CI na bieżącym commicie. Brak podbicia = release o tej wersji już istnieje, więc krok tylko wypisuje komunikat i kończy się sukcesem; **nowa wersja u operatora po prostu się nie pojawia**, i to jest jedyna kara za zapomniane podbicie.
  - Numery mogą przeskakiwać (commit bez pushu, kilka zmian naraz) — nic się przez to nie psuje.
  - Po co: operator dostaje baner aktualizacji tylko wtedy, gdy wydanie ma wyższy numer niż `APP_VERSION` w jego `.exe`. Wersja stojąca w miejscu mimo zmian to `.exe`, który kłamie o tym, co ma w środku.
- Komunikaty UI po polsku.
- Nazwy folderów sanityzowane przez `sanitize_name()` w `src/naming.py` (regex: tylko `[A-Za-z0-9_\-. ]`).
- Kod komentowany minimalnie, nazwy funkcji opisowe.
- `gitignore`: `.venv/`, `photos/`, `__pycache__/`, `.DS_Store`.
